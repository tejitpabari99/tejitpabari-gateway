## Notes (non-blocking)

- **Double-click Send or Test:** the first click sets `orgSaving` and disables both buttons before `saveOrganization` is sent (`index.html:387-388`). The second click is ignored by the guard (`:381`), and a disabled button does not fire onclick anyway. Only one save runs, so only one `onSaved`. `[verified: index.html:380-402; test ui-org "double-click Send/Test"]`
- **Gap between re-enable and re-disable after a successful save:** no async gap. The success handler calls `setFlowButtons(false)` and then `onSaved()` in the same task (`:391-394`). `doStartSending` reaches `confirm()` (modal and synchronous) and then `btn.disabled = true` (`:695-700`) without yielding. `doSendTest` reaches `testBtn.disabled = true` (`:610`) the same way. No click event can be handled between those lines.
- **Click during the confirm dialog:** blocked by the modal. After OK, `sendBtn` is disabled at the same time.
- **Send then Test, or Test then Send:** while the loop runs, `sendBtn` stays disabled until the loop ends, so `saveOrgThen` returns at `:381`. While a test send is in flight, `testBtn` is disabled, so Send returns too. There is no path to two loops, two test sends, or a loop plus a test running at once.
- **Buttons come back in every exit path:** save failure (`:396-398`), invalid org (returns before anything is disabled), missing selections or invalid startRow/limit (returns after the save already re-enabled them), confirm cancel (same), batch-init failure (`:722`), loop complete (`:771`), loop stopped after 5 errors (`:817`, `:845`), test success and failure (`:623`, `:635`). `[verified: tests "save failure re-enables", "confirm-cancel re-enables"]`
- **Send loop and reportBatch:** `sendEmailsSequentially` is untouched by 63f65c5. Each loop still creates one `runId` and reports through `reportOnce`. With a single loop guaranteed, double counting is gone.
- **Small UX change (accept):** during a batch, `testBtn` looks enabled, but clicking it silently does nothing, because the `sendBtn.disabled` guard stops it. Before this change a test could run alongside the batch. Blocking it is the safer behaviour. Disabling `testBtn` visually during the loop would be optional polish, and it is out of scope here.
- **Hung `saveOrganization` call:** if the call never returns, both buttons stay disabled until the page is reloaded. Every `google.script.run` call here behaves the same way, and Apps Script fails it on timeout. Accept.
- Security and architecture are unchanged from round 1. The fix is local and minimal, and it adds no new inputs or sinks.
